## 第一阶段验收目标

新接入受支持节点时，通过身份与连接配置完成登记，不修改控制中心源码。CLI 可以发现能力、执行操作、订阅数据和取得产物；发生断联、重启、资源冲突或重复提交时，结果仍然可信且可追溯。AI 仅通过机器接口完成相同流程。

此目标不等于第一阶段支持所有芯片、调试器或烧录方式。

## 建议顺序

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| M0 方案收敛 | 三个代表场景、对象边界、最小契约及目录决策 | UART、I²C 和烧录均可解释生命周期与异常路径 |
| M1 机器入口 | 版本化契约、基础 SDK、CLI、节点与能力查询、配置与身份模型 | 客户端不读内部数据库；身份、能力和错误可机器解析；新增实例无需硬编码 |
| M2 执行核心 | 操作账本、控制租约、资源调度、代理最终校验及现有驱动适配 | 重复提交、过期控制、断联、节点重启、资源冲突和未知结果有明确语义 |
| M3 数据与分析 | 多消费者数据流、原始产物、时钟来源、摘要及基本分析 | 多客户端不互相消耗数据；缺失与保留范围可见；分析可追溯到原始输入 |
| M4 开发闭环 | 构建输入、固件与符号关联、代理更新及一种完整目标烧录路径 | 能从构建追溯到实际目标和验证证据，恢复与失败路径可核对 |
| M5 实验复用 | SDK 示例、协作任务、有限本地动作序列及必要的流程编排 | 有边界、可恢复、可审计，清理步骤不会被错误跳过 |

已有 OTA 等能力可在对应阶段逐步迁入，不要求等待所有新模块完成后才可使用。
网关以明确的烧录、调试或构建用例驱动首个实现；Pico 2W 等新型号在公共契约可验证后再适配。

## 默认验证路径

1. 契约与纯逻辑验证：类型、参数组合、状态、错误、幂等和兼容性。
2. 服务与代理集成：身份、资源、账本、流和产物之间的边界。
3. CLI 场景：使用机器输出执行正常流程与必要的异常流程。
4. 针对变化的实板验证：明确硬件、接线、动作副作用和实际证据。
5. UI 定向验证：仅在界面或客户端接口发生相关变化时执行。

不为可逆文案或目录调整机械增加测试，不重复跑与本轮变化无关的 UI 流程。
模拟与真实硬件结果分别记录；未连接实际外设时，不把模拟或空总线验证当作该外设的数据验证。

## 三个场景的关键问题

| 场景 | 正常路径 | 必须讨论的异常 |
| --- | --- | --- |
| UART | 建立控制会话、写入、多个消费者读取同一有序流、结束 | 写入中断、溢出、游标过期、读者断开、节点重启 |
| I²C | 获取主机接口、调度总线、执行有限事务、保存原始结果 | NACK、线路被拉低、部分执行、重复请求、物理总线冲突 |
| 烧录 | 解析目标与镜像、核对兼容性、执行、校验、确认 | 目标识别不符、连接丢失、取消请求、写入结果未知、恢复失败 |

## 迁移完成依据

- 实际能力与身份不再散落于控制中心和网页的固定分支。
- 新旧入口使用统一控制权、资源占用与执行记录。
- 现有数据可核对，历史记录仍可查询；原始证据与派生结果不丢失关联。
- CLI 和 SDK 能完成主要开发闭环，AI 无需模拟点击或解析中文提示。
- 硬件动作仍受节点本地边界约束，客户端参数不能绕过。
- 构建产物、私人配置和可公开示例有明确存放与打包边界。
