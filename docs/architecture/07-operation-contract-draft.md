# 操作与机器接口契约草案

状态：待评审 v0.3，2026-10-27。对应 `contracts/drafts/operation-v0/`，版本标识为 `edbg.operation.draft/0`，当前服务仅复用请求 Schema 提供无副作用预检查，实际接口见 [工作空间参考](../reference/workspace-v0.md)；已建立 UART 受限兼容账本，见 [UART 参考](../reference/uart-operations-v0.md)；通用节点执行协议仍未实现。原 CLI 查询包络保持独立。

## 请求职责

| 字段 | 语义 |
| --- | --- |
| `api_version` | 明确使用草案或未来正式版本，禁止自动猜测 |
| `connection.id/revision` | 稳定连接身份及预期版本；动作提交不接受可变名称别名 |
| `action` | 有版本化语义的动作名称 |
| `params` | 动作专属参数，未知字段拒绝；字节用明确编码 |
| `idempotency_key` | 调用者生成，重试原意图时保持不变 |
| `timing.dispatch_within_ms` | 从接受起算的派发有效期；进入重试不能重新起算 |
| `timing.execution_timeout_ms` | 节点开始执行后的本地预算，不是客户端 HTTP 超时 |
| `preconditions.node_boot_id` | 可选的预期启动保护；服务仍必须冻结接受时解析的启动上下文 |

第一批有限动作默认只向当前可用节点派发，不提供隐式离线队列。接受之后失联时可在原派发期限和同一启动约束内等待；已经派发且执行可能发生时转入核对，不重新执行。会重启代理的动作另有明确的新启动确认路径。

服务端接受时冻结：调用主体、请求摘要、节点/目标/接口、连接修订、提供者与能力修订、启动上下文、镜像身份和资源计划。配置名称、目标别名、镜像标签或驱动默认值在执行时不得再次解析。事务型资源占用由服务端计划，客户端不能通过删减资源列表绕过冲突。

当前请求 JSON Schema 只描述形状与静态参数组合。它不能证明接线正确、节点在线、当前身份有权限、资源可用或驱动支持参数。后者必须由服务预检查与节点执行前校验共同完成。

## 接受与幂等

建议作用域为工作空间与主体：`(workspace_id, principal_id, idempotency_key)`，不按 action 分开，以防同一个键错误地执行两种动作。

1. 认证、限制请求大小并拒绝重复 JSON 键、非有限数值和未知字段。
2. 在同一数据库事务中检查既有键；原请求相同且有权访问时返回原操作，不重新解析当前连接版本。
3. 同键不同规范请求返回 `IDEMPOTENCY_CONFLICT`，不创建新操作。
4. 首次请求核对连接修订、能力、权限及执行边界，持久化操作、请求摘要与幂等关系后才返回接受。
5. 进程在提交后、响应前退出，重试同一键仍得到原操作。派发通过持久记录恢复，不依赖内存队列作为唯一账本。

规范请求包括版本、连接修订、动作、全部显式参数、前置条件和执行预算，排除幂等键与请求追踪标识。参数先按严格模式校验，再排序对象键；数组顺序保留，字节十六进制归一为小写。草案的数值字段使用整数；不对 `1` 与 `1.0` 等输入默默强制转换。规范化算法需版本化并有测试向量，不能只比较原始 JSON 文本。

幂等摘要和原操作身份应独立于大体积结果保留。结果被清理后，同键也不能再次执行；应返回原身份及结果已清理的信息。工作空间删除前保留键的墓碑关系是第一阶段建议，具体配额和归档规则需实施时明确。

认证失败、结构无效、连接修订不符等接受前拒绝，没有可执行操作身份。HTTP 响应丢失时客户端无法据此推断是否接受，必须用原键重试核对。失败不统一附带 `retryable: true`；应给出 `query_original`、`retry_same_key`、`new_intent_required` 或 `none` 等具体处理建议。

## 状态与结果

建议操作阶段：

```text
accepted → awaiting_resources → dispatched → executing → finished
                                  └────────→ reconciling → finished
```

箭头是典型路径，允许跳过无须等待的阶段。尚未派发也可因到期或取消进入 finished。`dispatched` 表示存在派发尝试，不证明节点收到；节点明确未执行的拒绝与可能执行后丢失确认要区别记录。

`finished` 的结果为 `succeeded`、`failed`、`partial`、`cancelled`、`expired` 或 `unknown`。只有未可能开始的操作才能判为纯粹的 `expired`；执行预算到期后应依据已经发生的动作给出失败、部分完成或未知。

结果另带资源状态：`held`、`release_pending`、`released` 或 `unconfirmed`。这里的 released 只说明该操作取得的占用已释放；UART 写入结束后，会话持有的 UART 资源仍由会话管理。计划含多个资源时须逐项记录，汇总不能隐藏某一项未释放。

`unknown` 允许客户端结束等待，不能作为安全重试或资源释放依据。迟到证据追加到同一操作并提升修订号，允许修正原结果；保留旧修订和依据，不自动触发第二次执行。未知结果不应使服务永久阻塞：是否可以重新执行由节点账本、启动核对、租约失效及驱动特定的恢复规则决定。

每种动作声明成功需要哪些证据。至少区分派发、节点接受、驱动完成、总线确认、读回校验和业务确认。服务不得用一个脱离动作语义的 `ok=true` 代替这些区别。

## 取消与期限

- 客户端 `--wait-timeout` 仅限制等待，返回操作身份和当前修订，不自动取消。
- `operation cancel` 提交取消意图；只有动作尚未派发或节点确认在安全点停止，才可判 cancelled。
- 取消与完成并发发生时，以执行证据决定结果；已完成操作的迟到取消不能覆盖成功。
- 关闭 UART、I²C 恢复、擦写停止、节点更新的取消行为分别定义，不存在统一的“设置所有引脚为输入”。
- 节点使用本地单调时钟执行预算。服务的墙钟期限与节点预算通过协议映射，不直接拿两台机器的时间戳相减。

## 资源与隔离

控制租约给出授权范围、持有者、期限与 fencing 编号；具体操作占用资源计划。多资源取得必须原子化或有统一顺序，不能每持有一部分就无限等待剩余资源。

共享物理实体使用工作空间内统一资源身份，例如两节点连接的同一 I²C 总线。GPIO、控制器、目标复位与电源等依赖由提供者和连接配置展开；客户端不自行声明完整锁集合。

第一阶段可以保守串行化当前适配器，明确记录“兼容适配器按节点互斥”。只有端到端资源检查完备后，才开放同节点并行，不能因为公共模型支持资源粒度就放松旧固件的实际限制。

控制转交需要节点确认旧持有者释放或满足明确的失效证明。服务重启、数据库租约到期或操作 finished 都不是充分证明。节点启动变化时旧 fencing 上下文失效；节点应拒绝旧启动及旧控制请求。

## CLI 与 API 对应

以下均为未来入口示意，不是当前 CLI 支持的命令：

```sh
edbg operation submit --file request.json --wait --wait-timeout 30s --json
edbg operation get op-123 --json
edbg operation watch op-123 --after 42 --format ndjson
edbg operation cancel op-123 --json
edbg stream read stream-123 --after cursor-123 --limit-bytes 4096 --json
edbg stream follow stream-123 --after cursor-123 --format ndjson
```

便捷动作命令与文件提交生成相同请求。机器调用显式提供并保存幂等键；人工便捷命令可生成键，但在首次发送前应保存到本机私有请求记录，以便响应丢失后核对，不能只把键存在进程内存中。

预检查或 plan 请求不下发、不预约、不打开端口；返回配置/能力修订和预计资源，不能保证后来一定可执行。实际提交仍完整检查。

事件使用操作内单调序号，重连可能重复，消费者按身份去重。读取带游标、保留范围和缺失说明；事件输出不会携带大块二进制，使用产物引用。完整事件与流分页契约仍需下一轮细化。

## 仍需确认的实现参数

本轮优先评审语义，暂不冻结 HTTP 路由、正式版本名、状态枚举、租约数值、保留配额和芯片链路编码。下一批先实现版本化连接与无副作用预检查，再以 UART 写入接入首个持久操作闭环；不会同时重写所有外设。
