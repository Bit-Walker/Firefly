# 系统目标与功能范围

状态：建议基线 v0.2。更新日期：2026-10-26。

## 定位

系统为分散部署的嵌入式设备提供开发、控制、观测和分析闭环。人类可以使用 CLI 或网页，AI 和脚本可以使用机器接口；操作、权限、资源管理和结果判断共用同一套核心逻辑。

完整闭环是：发现节点与能力 → 核对目标及连接 → 获取控制权与资源 → 执行操作 → 保存证据 → 分析结果 → 决定后续动作。

公共模型不绑定某个 MAC 地址、永久的 A/B 角色或某个实验接线。板级限制由板卡描述和驱动表达，部署身份、接线和用途由配置表达。

## 功能地图

以下是目标范围，按阶段实现，不是当前功能清单。

| 功能域 | 目标能力 |
| --- | --- |
| 节点与身份 | 注册、分组、在线状态、运行代理、启动批次、能力发现、节点代理更新 |
| 目标与连接 | 自身或外接目标、接口映射、接线关系、配置版本、资源归属、占用与租约 |
| 构建与产物 | 源码与构建输入、工具链记录、固件与符号文件、内容校验、产物追溯 |
| 烧录与升级 | 节点代理更新、目标应用更新、外部目标烧录、校验、恢复和结果确认 |
| 硬件交互 | UART、GPIO、I²C、SPI、有限信号发生及后续协议扩展 |
| 调试与观测 | 日志、指标、数字采集、协议解码、崩溃分析、由适配器提供的深度调试 |
| 实验与自动化 | 多节点协作、条件执行、有限并行、清理步骤、可复现实验与报告 |
| 数据与分析 | 有序流、历史查询、原始数据、派生结果、时钟来源与证据关联 |

节点代理更新和目标固件烧录是不同操作。OTA 是一种更新路径，不是所有烧录能力的公共定义。

## 节点与硬件演进

第一阶段继续使用已有 ESP32-S3。架构需要容纳后续 Pico 2W 及现场 Linux 网关，但具体移植、烧录接线和驱动实现留待对应阶段验证。

微控制器节点执行受支持的本地硬件动作；网关节点可以承载 USB、串口、构建工具和外部调试程序。深度调试可能需要独立探针或网关：目标停在断点时，目标自身的网络代理未必还能工作。

不同型号不必支持同一份功能集合。统一的是能力发现、调用、资源管理与结果语义，而不是虚构所有硬件都有相同接口。

## 第一阶段边界

- 单用户、自建部署，控制服务在逻辑上分模块，部署上保持简单。
- 为人、AI 和脚本保留独立身份、授权范围与执行预算。
- 优先稳定机器接口和 CLI，再按需求调整 UI。
- 时序敏感的动作尽量下沉到执行节点，不依赖控制中心逐个翻转引脚。
- 先用 SDK 和脚本形成实际实验流程；不提前建设通用脚本语言或完整工作流平台。

## 现有实现的位置

`fleet/` 是现有原型，已具备 ESP32 节点管理、OTA、日志、远程 UART、有限波形采集和 I²C 功能。实际支持范围及验证见 [现有说明](../../fleet/README.md)。

后续重点是把已有能力迁入统一对象与执行模型，去掉具体设备身份、角色和物理总线关系在公共逻辑中的硬编码。现有硬件驱动中必要的电气和时序边界仍需保留。

架构方案不代表已经支持任意芯片烧录、任意引脚、实时多节点同步或所有调试协议。
